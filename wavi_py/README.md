# wavi_py

Python port of [`wavi/wavi.m`](../wavi/wavi.m) — the whisker-sensor DAQ client. Same wire format, same `.dat` recording format, same three views (line / FFT / spectrogram). No MATLAB dependency.

The architectural difference from the MATLAB version: **data acquisition is decoupled from visualization** via a thread-safe `SampleBus`. The GUI is one subscriber; an agent control loop on another thread is another. Slow GUI redraws can never starve a tight control loop, and vice versa.

## Install

```bash
pip install -r wavi_py/requirements.txt
```

Dependencies: PyQt6, pyqtgraph, numpy, scipy, pyserial, and PyOpenGL for the Dome view only (everything else runs without it). On Windows `pip install PyOpenGL` (or `pip install -r wavi_py/requirements.txt`) is all it needs; the GPU driver provides OpenGL.

## Run (GUI)

Against the Pi bridge (`rpi/daq_bridge.py` running on the Pi):

```bash
python -m wavi_py --transport tcp --host 192.168.2.3 --port 5555 --nsensor 9 --fs 80
```

Against the BlueROV2 whisker array + IMU (`rpi/daq_server.py` on the vehicle; see [rpi/README.md](../rpi/README.md#bluerov2-whisker-array--imu-server-daq_serverpy)):

```bash
python -m wavi_py --transport server --host 192.168.2.2 --scale 0.2
```

This adds an **IMU** view (accel, gyro and attitude on the IMU's own time axis, over the same span as the whisker plots and independent of the whisker scan rate, with the stream status line and the alarm banner), and **Rec** records on the vehicle as well as locally (`.dat` + full `.jsonl`).

**Rec with the vehicle.** The recording on the Pi keeps running when wavi_py disconnects or crashes (a Disconnect or closing the window stops the one this window started). Rec sends `rec_start` and starts the local files when the server's reply comes in (the button says *Starting…* meanwhile). The button follows the status record: if the ROV records and this window didn't start it (the other client's, or this one's from before a crash or reconnect), it turns orange, **■ Stop ROV rec Ns** (hover: file, who started it, time left), the status line shows the file and `by … (not ours)`, and clicking it asks, then sends only `rec_stop` for that file. It never starts a recording over a running one, and nothing is recorded locally for one it didn't start (its file on the Pi is the record; a local copy from the middle would start without the window's `.dat`). If another client started one between two status records, the server refuses the start and wavi_py asks: **Replace** (closes that file, starts yours) or **Keep**. **Auto-stop** sends its time as the recording's duration, so the server stops it even if wavi_py is gone; the stop shows up here as a normal stop (local `.dat` and `.jsonl` closed, the label says "stopped by the server: duration 60 s elapsed"), and wavi_py stops on its own 3 s later only if the server didn't (an older daq_server). Likewise a stop from elsewhere (the other client, `rpi/scripts/rec.py stop`) ends the local recording too. **Mark bad** (next to Rec) writes a flag into the recording's notes (see "Notes and recording cards" below) and, with the vehicle live, also flags the newest ROV recording (the running one, else the last; hover for its name) as bad in the Pi's recording index, with an optional reason. The file stays, and `whisker_link.convert` skips it. Once flagged, the button reads **Unmark bad** and undoes it. The Pi side needs daq_server 0.3; an older one replies that it has no index. See rpi/README, "Recording index". Older daq_servers work as before.

Against the ESP32 whisker DAQ ([`msd/esp32/whisker_daq`](../msd/esp32/whisker_daq/)) plugged directly into the PC by USB, for bench work without the ROV:

```bash
python -m wavi_py --transport esp32 --serial-port COM5
```

wavi_py decodes the ESP32's binary frames itself (921600 baud, sends `B` to start streaming), so everything behaves as with `--transport server` except that there is no IMU and **Rec** writes only the local `.dat` + `.jsonl`. The status line shows the scan rate and the same error counters. wavi_py deasserts DTR / RTS before opening the port so as not to reset the ESP32, but if it does reset (some USB-UART drivers toggle DTR anyway, or a watchdog) it comes back in its boot default: wide 250 Hz, OSR 128 with selects 0123457 (firmware since 2026-10-28; earlier firmware: quiet 62.5 Hz, OSR 512 with all 8 selects); see **Scan mode** below.

**Scan mode** (second row of the Sensor array box; Server, ESP32 and Sim transports) switches the ESP32's scan mode without a reflash: **legacy** (`M0;`; its rate depends on the selects, ~89 Hz with 7), **quiet 62.5 Hz, OSR 512** (`M1;`, the boot default of the firmware from 2026-10-23 to 10-27), **quiet 62.5 Hz, OSR 256** (`M1 200 256;`), **quiet 125 Hz, OSR 256** (`M1 200 256 8000;`) and **wide 250 Hz, OSR 128** (`M2;`, the firmware's boot default since 2026-10-28, with selects 0123457); see [Locked scan modes](../msd/esp32/README.md#locked-scan-modes-quiet-625-hz-wide-250-hz-2026-10-22). Picking one sends `S<selects>;M<args>;B` through the `esp32` command (with `--transport server`, daq_server passes it on to the ESP32); **Selects** (default `0123457`, empty = all 8) goes with it. **as is** (the default) sends nothing. Next to it, and at the end of the status line, is what the ESP32's INFO frame reports, not what was asked for: "quiet 125 Hz OSR 256 confirmed", or in red "NOT SET ..." with the reason when no INFO matches within 2 s (no reply, or the firmware refused it, e.g. `M: scan period not a whole number of conversions at this OSR`). The ESP32 boots in wide 250 Hz, OSR 128 (core C1) with selects 0123457 (earlier firmware: quiet 62.5 Hz, OSR 512 with all 8) and forgets any mode setting on reboot; the GUI goes by the INFO, not by an assumed boot state, so when an INFO later reports another mode or other selects, the choice is re-sent once and the note says what the ESP32 came back in (e.g. "re-applied HH:MM:SS after the ESP32 came back in quiet 62.5 Hz OSR 512 selects 01234567" with the older firmware); if that doesn't stick either, it is reported and not sent again until you pick a mode (picking the same one again retries). `--mode` sets the startup choice, with the same spelling as daq_server's `--mode` (`legacy`, `quiet`, `wide`, `quiet,200,256`, `quiet,200,256,8000`), and `--selects` the selects; on connect it is sent only if the ESP32 isn't already in that mode. A daq_server started with its own `--mode` re-sends that one on every stream start; the GUI then re-applies its own choice once, as after a reboot.

**Reset ESP32** (end of the Scan mode row; Server, ESP32 and Sim transports, enabled while connected) reboots the ESP32 by an RTS pulse on its USB-UART, the same as pressing EN: through daq_server (`{"cmd":"esp32_reset"}`) with `--transport server`, on the serial port with `--transport esp32`, and the Sim reboots. It asks first, since streaming stops for a few seconds (a running recording keeps going with a gap). The status line then shows the reply: "EN pulsed, it is rebooting", or "failed: <reason>" (e.g. the port isn't open, or no RTS line, as on daq_server's fake ESP32 pty), or "no reply" after 3 s (a daq_server older than this button). The ESP32 comes back in its boot default and Scan mode re-applies the choice. It doesn't power-cycle the whisker PCB, so it can't clear an ADC lock-up.

**ADC fault alarm** (Server, ESP32 and Sim transports). On the ROV the whisker PCB runs from vehicle power and its ADC can lock up so that only a PCB power cycle clears it. The fault model (`whisker_link/esp32_fault.py`, run by daq_server or by the ESP32 / Sim transport) turns the firmware's signals into a state in the status record, and wavi_py shows it as a banner on top of the panel and of every plot window. The banner does not block plotting. **Red (fault, latched):** `[halt #N] UNRECOVERED`, CLOCK config not accepted (at boot, on `M`, after an ADC reset), ADC not answering, repeated `[halt] no conversion` in a locked mode with no scans for 1.5 s, or no scans for 5 s while connected. It says what to do: "Power-cycle the whisker PCB (vehicle power)"; for no scans, check the ESP32's USB link. A later INFO doesn't clear it. It clears only after 10 s of clean streaming: after a PCB power cycle with the ESP32 running, the firmware recovers by itself. **Amber (warning, for 60 s):** recovered halts, ADC resets, reader-watchdog and other unexpected ESP32 reboots, `[idf]` errors, and more than 1 % of scans flagged SYNC/EMPTY over 10 s. **Fault log** (Status box, counts the events, red or amber while active) lists every onset, warning and clear of the session. While recording, each event also goes into `<recording>.faults.txt` next to the `.dat`, with its wall time and the `.dat` row it falls on; a fault already active at record start is written first. The `.jsonl` gets it as a `mark` event (`text` + `fault`), which `whisker_link.convert` lists under `mark_t` / `mark_text`. The status line starts with `FAULT <code>` while a fault is active. With firmware 2e9d8dc or later the status line also ends with the ESP32's 1 Hz heartbeat (`esp32.beat`) as `ADC 7812 conv/s` (DRDY edges per second: 7812 in quiet OSR 512, 31250 in wide, 3125 in legacy), in red as `ADC NOT converting` when the ADC stops; after a reboot it shows `ESP32 rebooted HH:MM:SS (reset: <reason>)` for 30 s (`booted` if the ESP32 came up less than 30 s before connecting), and the Fault log gets that line once.

After a switch the rate follows the INFO: scan_hz for the locked modes, and for legacy the rate measured earlier for the same selects, else an estimate from the select count (1.6 ms per select), replaced by the measured rate ~2 s later. The rolling buffers start over at the sample where the INFO arrived, so no plot or FFT / Spec window mixes two rates, and the time axis and the `.dat` timestamps continue from there at the new rate (a measured-rate correction is now applied while recording too, for the same reason). With `--fs` given, the rate stays fixed. The `.dat` timestamps count samples, so a stretch with no scans (a reboot, a dropout) takes no time in them.

Without any hardware, against a simulated 16-whisker array (any OS; no server, no serial port):

```bash
python -m wavi_py --transport sim
```

or pick **Sim** in the transport list. It sends the same event stream as the ESP32, so the plots, V0 / Re-zero, the measured rate, the status line and **Rec** (`.dat` + `.jsonl`) all work as with the real array; there is no IMU. **Signals** (next to Connect) opens a panel that changes the signals live, also before connecting: per gauge live or open (railed), a sine (amplitude, frequency) and white noise (RMS; **Noise (all)** sets every gauge at once); scan rate in the legacy scan mode (40 to 1000 Hz; the GUI adopts a new rate in one step), drift, and mains hum (amplitude at 50 or 60 Hz, picked up by each gauge with its own fixed coupling 0.3 to 1.5; evaluated at the scan times, so below 2× the mains frequency it aliases, e.g. 50 Hz at 80 Hz scans shows at 30 Hz); presets (demo, all live at 1 to 16 Hz by whisker, all live at 2 Hz, all open, noise floor with every gauge live at 0.05 to 0.5 mV of noise, noisy gauges, hum 50 Hz, hum 60 Hz, and bench: small sines, spread noise, 1 mV of 50 Hz hum and a slow drift; hover the preset list for details); taps, a decaying ring on one whisker (by hand or every few seconds; "any" picks a whisker with a live gauge); and faults (ADC recovered / CRC retry / stale / re-init, a sequence gap, a link CRC error, a 3 s dropout) that show up in the status line's counters, **Reboot ESP32** (like the firmware it comes back in wide 250 Hz with selects 0123457 ~2 s later, so Scan mode re-applies its choice; the array also starts in that mode, so the scan-rate setting applies only after picking legacy), and **ADC lock-up** / **Power-cycle PCB**. The lock-up stops the scans and makes the firmware report `[halt #N] UNRECOVERED` every 1.5 s in legacy, or five `[halt] no conversion` and then `[halt #N] UNRECOVERED` every 5 s in a locked mode; a reboot meanwhile shows CLOCK not accepted. The Sim also sends the firmware's 1 Hz heartbeat (0 conversions/s while locked up). The power cycle recovers it, as with the real board. Use these to see the ADC fault alarm. The Sim transport also takes the Scan mode commands like the firmware (`S`, `M` checked as the firmware does, `B`): the locked modes run at 62.5 / 125 / 250 Hz with a HEALTH record, and the outputs of skipped selects read open. Switching a gauge from open to live mid-stream puts a step in its trace until **Re-zero**, as plugging in a real gauge would. Scripts can use it too: `WaviClient(transport="sim", nsensor=16)` and edit `client.sim` (a `SimSignals`: `preset()`, `set_channel()`, `tap()`, `fault()`, `rate_hz`, `noise_mv` (per gauge), `drift_mv_s`, `hum_mv`, `hum_hz`).

Against an Arduino plugged directly into the PC:

```bash
python -m wavi_py --transport serial --serial-port COM3 --nsensor 9 --fs 80
```

Click **Connect**. Toggle **Line / FFT / Spec** to bring up plot windows. **Pause** freezes plot updates while data keeps flowing (and recording continues). **Rec** writes a `.dat` file using the exact MATLAB filename / line format, so existing tools under [`data_processing/`](../data_processing/) keep working unchanged. **Auto-stop** (Record row) is a toggle and a box of whole seconds (5 s to 10 h, arrows step 5 s): with the toggle on, each recording stops after the box's time and the progress bar fills meanwhile. The box keeps its time while the toggle is off, and typing a time (Enter or leaving the box) or an arrow step turns the toggle on, as typing a colour range switches the FFT / Spec Auto off. With daq_server the time goes to the server with the start, so both controls are fixed until that recording ends.

**Ctrl+R** in any wavi_py window (the panel or a view window) does what a click on **Rec** does: start, stop, or stop the ROV's recording that isn't ours (asking first). It follows the button's state, so in replay or while the server's reply is pending it does nothing and says why (panel status line, and the window's status bar). The view windows' plain **R** stays Reset view. Every plot window (Line, Spectrum, FFT, Spec, IMU, Dome, ROV) shows the recording at the right of its status bar: with Auto-stop a bar filling red toward the stop time (**REC 0:42 / 1:00**), without it a full red bar with the elapsed time, grey **not recording** otherwise (and **Starting…** while the server answers, orange for a vehicle recording this window didn't start). The panel's Rec state and clock are the one source; the windows only show it.

A view turned on in the panel comes to the front (raised, un-minimized, focused). Each view window's toolbar starts with **Go to**, a menu of the control panel and every view (ticked: open): picking one opens it through its panel button if it is closed and brings it to the front either way. The panel is narrow (about 440 px, 460 px with the replay timeline): the buttons sit in two rows per group, long labels (scan-mode note, paths, the timeline's readout) are cut instead of widening it.

The **Line** window has its own **Pause** and **Re-zero** buttons, which are the control panel's Pause and Reset (re-capture the V0 baseline) and stay in sync with them. It opens in the **Grid** layout (one tile per whisker); untick Grid for the stacked layout (all whiskers on one axis). Double-click a tile (or, in the stacked layout, near a whisker's trace) to show that whisker alone, and double-click again, press Esc or click **All whiskers** to go back.

Zoom and live: time (X) is always shared by all plots; **Link Y** (Y; on by default) gives all grid tiles one Y range, and turning it off gives each tile its own. The plot buffers keep the newest 90 s (`--t-buffer`, `DEFAULT_T_BUFFER_S`); the Line and IMU windows open on the newest 30 s (`DEFAULT_VIEW_SPAN_S`) and zoom out (- or the wheel) to the whole buffer. While live, the plots show the newest part of the buffer, and zooming time keeps them live (the right edge stays at now). Panning time or zooming / panning with the mouse leaves live; **Live** (L) goes back to live keeping the zoom (time span, Y ranges, gain), and so does Resume. **Reset view** (R) also restores the 30 s span, auto Y and gain 1. Paused, the window keeps the buffer as it was at the pause, so the whole 90 s can be looked through. The 90 s buffer costs no more than 30 s per tick: the whisker buffer is a ring (`daq/ring.py`: the newest samples stay one contiguous array, so every reader slices it as before, and a tick writes only its new samples; the newest rows are copied back to the start once per buffer length, every 90 s), Spectrum, FFT and Spec only ever read their newest window, the Line window reads the buffer in place (a copy only when paused) and decimates the visible span only, and the buffers are a few MB more (no change in peak RSS). The IMU buffer (~100 rows a second) is rebuilt each tick instead (~20 µs at 90 s), so the IMU, ROV and Dome windows can keep the arrays they were given. Measured with `viz_bench --windows line,fft,spec,imu --t-buffer 30|90` at 250 Hz after the buffer filled: the tick is 2.0 ms either way (2.2 / 2.8 ms with the shifted buffer it replaced), the Line redraw ~4.5 + 11.5 ms paint at the 30 s span; zoomed out to all 90 s the Line redraw is 8.5 ms, and the render budget then slows FFT / Spec from 3.7 to 2.5 fps while Line keeps 20. **Y auto** / **Y fixed** (toolbar, with a ± value box in mV): auto is the per-tile auto-range above; fixed gives every tile, the single-whisker plot and every stacked row the same ± value around zero, so the channels compare by eye. The traces are drawn minus V0, so zero is each channel's own baseline and the gauges' different DC offsets are already gone; a channel that drifts out of the window comes back with Re-zero. While fixed, the Y keys change the ± value (all plots alike) and Reset view keeps the fixed range; typing a value switches to fixed, and Y auto restores the dynamic ranges. Keys (the **Keys** button lists them): **Space** pause / resume, **L** live, **R** reset view, **=** / **-** zoom time in / out (keypad + / - too), **+** / **_** zoom Y of the framed tile (the one last under the mouse, with an orange frame; all tiles if none), **.** / **,** zoom Y of all tiles, **arrows** move the data (Left slides the traces left, Up slides them up; Left / Right all plots, Up / Down the framed tile), **Y** link Y, **Z** zoom box, **0** re-zero, **Esc** back to all whiskers. In the stacked layout the Y keys change the trace gain (shown on the axis label) instead, so small signals grow while all rows stay in view. The right side of its status bar shows the same stream status line as the control panel (scan rate, error counters), also while recording and when the control panel is hidden; when a message is shown on the left, the status line is shortened from its start.

**Spectrum** opens a live amplitude spectrum per whisker in the same layouts and with the same keys (grid by default, Link Y on by default, framed tile, double-click for one whisker, Pause in sync with the control panel); X is frequency, linear, 0 to fs/2. Each update takes the newest 1 s of every channel (W cycles 0.5 / 1 / 2 / 5 s; the bin spacing is 1 / window), removes the mean, applies a Hann window and scales the rFFT so a sine of amplitude a reads a, in the Line window's units (mV at the ADC times `--scale`). The mean is removed rather than a linear trend: with a 1 s window a 1 Hz sine is a single cycle, and a fitted line would take about 45 % of it. **dB** (D) shows dB re 1 unit, leaving out constant (railed) gauges. Each tile's corner shows the dominant frequency (largest bin above DC) and its amplitude per gauge; in the stacked layout the Y keys set a gain (in dB, one row spans -60 to +20 dB times the gain). **Y fixed** gives every plot (and stacked row) the same range: 0 to *top* (linear), or *top* dB down to *span* dB below it (dB; 20 dB is a decade); linear and dB keep their own values, and the Y keys change *top* (linear) or *span* (dB). It is computed only while the Spectrum window is shown and not paused, at the 20 Hz UI tick.

**FFT** and **Spec** use the same spectra (newest FFT-window seconds, mean removed, Hann window, amplitude-scaled) and share a toolbar: **dB** (D), colour range **Auto** (A; 1st to 99.5th percentile of what is shown) or typed **min** / **max** (typing switches Auto off; linear and dB each keep their own range), **FFT** window length 0.5 / 1 / 2 / 5 s (W; one setting for both windows, so the bins are 1 / window apart), **Reset view** (R), **Pause** (Space, in sync with the control panel), **Keys**; = / - zoom the frequency axis from 0 Hz, the mouse reads channel, frequency and amplitude into the status bar, whose right side shows the stream status line. The **FFT** window shows a heatmap of channel by frequency with a colour bar, and below it, in a closed frame, a per-channel summary of the frequency band set right above it: **Peak bars** (the largest amplitude in the band), **Box over frequency** (the spread of the channel's amplitudes across the band: box 25 to 75 %, line the median, roughly the noise floor, whiskers 5 to 95 %, dot the peak) or **Box over time** (the default: the spread of the band peak over the last *history* seconds of data, i.e. of recording time in a replay at any speed; dot the newest frame); M cycles them. Open gauges are left out. The lower plot's Y auto-ranges while the colour range is Auto; with typed min / max it uses that range too, so heatmap and bars share one fixed scale (peak bars then rise from the min). The **Spec** window shows time by frequency for all channels stacked (each channel a row band, 0 Hz at its bottom) or one gauge with its frequency axis in Hz ([ and ] step through them), over a 10 / 20 / 60 s span; it gets a column every 4 samples but at most 20 a second (every 13 samples, 52 ms, at 250 Hz), each the spectrum of the FFT window ending at that sample, and the history is kept while the window is closed.

**Dome** (prototype) shows the 12 wired whiskers bending live on the whisker dome in 3D (pyqtgraph.opengl, needs PyOpenGL). The dome mesh and each hole's root, axis and bending frame are assets exported offline from the rov-cad dome (`wavi_py/tools/export_dome_assets.py`, run in the build123d env; output in `wavi_py/assets/dome/`, plain .npz + JSON so a web front end can reuse them). The pose model is `whisker_link/dome_pose.py` (numpy, no Qt): tare per channel (automatic on connect and on Reset, the **Tare** button, optional **Drift removal** with a 60 s time constant), a 30 ms low-pass, a 2x2 calibration per whisker from (A, B) mV to two bend angles, and the shape, a constant-curvature compliant root (11.5 mm, as in `data_processing/bend_angle.m`) under a rigid shaft. **The channel-to-hole mapping, the calibration (1 deg per mV, gauge A toward the dome's front, B sideways) and the bend model are placeholders**, each one table or function in `dome_pose.py`. **Gain** exaggerates the drawn angles; colour is the drawn bend magnitude (viridis, 0 to 45 deg; grey = no data: railed gauge or tare in progress). **Whiskers** draws them as tubes, lines (cheaper) or not at all (off: only the marks). The view reads the sample bus with its own cursor on its own timer (**fps**, default 60), independent of the scan rate and the 20 Hz panel tick, and stops while hidden or minimised; the status bar shows the measured fps, the per-frame pose / upload / draw times and the CPU load of the GUI thread and of the process. The second toolbar row is the **scribe shell**, a display aid: an imaginary sphere on the dome's hemisphere plus a cylinder down the tube axis, concentric with the dome, drawn as a grid (latitude rings and meridians on the sphere, rings and axial lines on the cylinder; **Grid** and **Surface**, a faint translucent skin, toggle separately). The cylinder grows downward (in R/4 steps, up to 10 R) when a tip goes below its end, so the trails stay on the drawn shell; it shrinks back when the trail restarts (gain, pivot or radius change). **Pivot centre** (the default) turns each whisker about the dome centre (about the axis point at its own height for a whisker on the cylinder part), so its tip moves on the shell, where a bend of phi times the gain is that many degrees of arc; the whisker is drawn straight from its hole to that tip. **Pivot root** is the physical model above. Each tip leaves a trail of the last **Trail** seconds (0.5 to 10, default 2, fading with age, coloured by bend). **Grid** sets the spacing in degrees of bend (auto: a 1-2-5 value near 12 deg on the shell at the current gain), and the readout next to it gives the same spacing on the shell in degrees and mm. **R** is the shell radius (auto: where the tips are at rest, mean root distance from the pivot + whisker length, 186 mm). On the cylinder part an axial bend moves the tip R tan(phi) rather than R phi, so the grid there is only accurate for small angles. **Neutral** puts a dot at each whisker's zero-bend tip (on the shell in centre mode, the rest tip in root mode) and **Arrows** draws an arrow from that dot to the current tip along the tip's way (a great-circle arc on the sphere part, a curve on the cylinder); each has its own toggle. **Marks at** roots moves the neutral dots, arrows, trails, grid and surface from the tips onto the dome's own surface (1.5 mm above it): each bend is mapped about the dome centre as in centre mode, so a bend of phi times the gain is that many degrees of arc on the dome; pair it with Whiskers off (key 0 then zooms to the dome). **Show** plane map replaces the 3D scene with a flat map of every whisker at once, as a pilot inside the ROV sees them: the port array on the left and starboard on the right, each side as seen from inside facing it, so its front column is toward the centre line and its back column lateral (x = distance aft of the foremost root plus a gap, y = root height). The roots are joined by grid lines; each whisker shows its neutral dot at the root, the arrow to its tip (drag toward the side's front, lift up; the dome's radius in mm per radian of bend, as with Marks at roots) and its trail; rings round each root mark the grid step (auto: about a fifth of the root spacing). The map pans with a left drag and zooms with the wheel; 0 fits it again. The Sim transport's **dome** preset drives the 12 wired gauges with slow sines, B a quarter cycle after A, so each tip circles.

**Dome map** (`--dome-map FILE`, default the ROV dome; `--dome-map none` or the **Map** button's None for plain W1 .. W16 and the placeholder holes; the Map button also loads another file). A JSON file keyed by the physical position on the dome, e.g. `LFM` (L/R = the ROV's port/starboard, F/B = the hole column nearer the dome's pole / at its widest part, U/M/L = up/middle/lower on the ROV). Each position's `daq` names the gauge channel of each bend axis, `drag` (front-back) and `lift` (up-down), as the stream names it (`W6_A`; `W6A` accepted), with a polarity (`{"ch": "W6_B", "polarity": -1}`; a bare name is +1; a dead gauge is `{"ch": null, "reason": "..."}` and reads as zero bend); the two axes may come from different slots. A position also has the sensor mounted there (`sensor_id`, may be null), a free-form `label` and the hole's `root` and `axis` (optional `e1` = drag direction, `length_mm`) in the collar frame. `unused_gauges` lists the other gauges with why (dead, not scanned, alive but unused). Calibration belongs to the sensor, so it is a separate file keyed by `sensor_id` (`calibration_file`, relative to the map) in the sensor's own axes: a 2x2 `deg_per_mv` from (drag, lift) mV to (drag, lift) deg (or `[g_drag, g_lift]`), plus `date`, `source`, `note`; it follows the sensor when it moves. The order: raw mV of the two gauges -> tare -> polarity -> the sensor's 2x2 (the placeholder 1 deg per mV without one) -> bend angles, drag + = tip toward the front, lift + = tip up -> the hole's frame. With a map, the per-whisker plots name each slot `LFM (W6)` (unmapped slots stay `W3`), the per-gauge ones (Spec, FFT status line) `LFM drag (W6_A)` / `LFM lift (-W6_B)` (`-` = flipped), and the Dome view uses the map's positions as its holes and labels them (**Labels**). The ROV dome as wired on 2026-10-29 is `wavi_py/assets/dome/dome_map.json`: drag = `Wn_A`, lift = `Wn_B`, coordinates from the CAD holes (accepted as accurate enough, not measured on the built dome), the port lift gauges flipped (verified on the bench 2026-10-30: gauge A on the back face on both sides, gauge B on top on port and on the bottom on starboard; see its `polarity_note`), and an empty `whisker_calibration.json`. The format and its checks (duplicate positions / gauges / sensor ids, unknown channels or fields, polarity +-1) are in `whisker_link/dome_map.py`.

Dome view camera: **left drag tumbles freely in every direction** (a trackball, `views/dome_camera.py`; pyqtgraph's own orbit stops at +-90 deg elevation), Shift + left drag rolls, Ctrl + left or middle drag pans, wheel or right drag zooms. The **view cube** (top right) turns with the scene; click a face to snap to it. Keys (and the **View** menu, whose tooltip lists them): **1** front, **2** back, **3** top, **4** bottom, **5** starboard, **6** port, **0** the default 3/4 view. The scene is rov-cad's collar frame, which in ROV terms is **+z forward** (the tube axis, the dome being the nose), **+y up** (the ROV's underside is -y) and so **-x starboard**, +x port; the triad (bottom left, Up / Fwd / Stbd) and the green **UP** arrow above the shell (with a **FWD** label at the pole) show it. Front looks aft at the nose (port on the right), top has the nose up the screen, starboard has the nose to the right. This assumes the dome is mounted as the ROV's nose, as the asset's frame note says.

Each plot also shows the current absolute value of both gauges (raw mV at the ADC, before the V0 subtraction and the `--scale`; mean of the last 0.1 s, refreshed ~7 times a second) in its corner, or on the right of each row in the stacked layout; a railed gauge (nothing plugged in) reads **open**. With the TCP / Serial (Arduino) transports the values are shown without a unit and never as open. Curves are min/max decimated to at most two points per pixel column and drawn with 1 px pens, so the redraw cost does not grow with the sample rate or the span shown. The Line and IMU windows read their data through one API, `daq/series.py` (`get` / `envelope` / `channels`: channels by name over [t0, t1], whisker and IMU alike): live from the rolling buffers (`MainWindow.series()`, the Line window's own paused copy), in replay from the whole recording (`replay/store.py`). All plot windows are redrawn by one render scheduler (`views/render_sched.py`): new data only marks a window dirty; Line redraws at most 30 times a second, Spectrum / FFT / Spec at most 10, IMU 20, one window per event-loop pass (so the Dome view's frames and input get in between), nothing while hidden or minimised, and when all windows together take more than half the GUI thread the spectra slow down first while Line keeps 20 fps. Y auto is fitted by the window and only re-ranges on a real change, the grid tiles share their axis pictures, and the spectrogram history is a ring the windows read when they redraw. `python -m wavi_py.tools.viz_bench --windows line,spectrum,fft,spec,imu,dome` measures any set of windows on the Sim transport (fps, redraw / paint ms, GUI-thread CPU, worst stall). On the cluster (250 Hz, 16 whiskers, software GL) the Line grid went from 78 % to 32 % of a core, the Spectrogram from 97 % to 12 %, and with every window open from Line 4 / Dome 4 fps to Line 18 / Dome 29 fps (the software-GL Dome blocks the GUI thread; a real GPU does not). `WAVI_PG_OPENGL=1` draws the plots through OpenGL viewports instead (slower on software GL; try it on a real GPU with `viz_bench --opengl`).

**ROV** (Server and Replay transports; needs PyOpenGL) shows the vehicle's attitude and translational acceleration from the IMU on a BlueROV2 model (`views/rov_view.py`): a decimated silhouette of Blue Robotics' public BlueROV2 R4 CAD (frame, thrusters, enclosures, buoyancy; CC BY 4.0, see `assets/rov/SOURCE.md`, rebuilt by `tools/export_rov_mesh.py` from rov-cad's `render/tessellate_bluerov2.py` output) with the whisker dome on its nose, turned by the ATTITUDE roll and pitch over a level grid (**Heading** adds the yaw, relative to the heading at the last Tare). Arrows from its centre, drawn over the hull, give the translational acceleration (`daq/imu_pose.py`: RAW_IMU specific force + gravity from the attitude, minus the at-rest bias, averaged over **Smooth** seconds): the resultant in orange and, with **Components**, surge (blue), sway (red) and heave (green, down +) along the body axes, at **Scale** mm per 100 mg; the readout in the corner gives the numbers. **Tare** takes the second round the shown time as rest (zero acceleration, straight ahead); the first second after a connect is taken automatically. The bias matters: on pilot2 the accelerometer and the EKF's level disagree by ~1.5 deg of pitch, ~30 mg. It draws whatever IMU buffer the panel holds, so it follows live data, a replay, or (paused live) the time picked on the timeline. The Dome view's **ROV** box puts the same model behind the dome. Its **Inertia** box tilts the Dome view's whole scene (dome, whiskers, marks and, if shown, the ROV) by the same roll and pitch, about the dome centre (the vehicle's centre with ROV on), over a grey ring in the level plane; the camera stays put, so a nose-down vehicle is drawn nose-down. It follows live data and replay alike, and the picked time when paused; heading is not applied, and with no IMU rows (Sim, ESP32, a `.dat` replay) the scene stays level. With more than one GL window the GL contexts must be shared (`Qt.AA_ShareOpenGLContexts`, which `python -m wavi_py` sets before the app starts; a script that builds `MainWindow` in its own QApplication must set it too).

## Replay

A daq_server recording (`.jsonl`: the Pi's `whisker_rec/*.jsonl`, or the local copy Rec writes next to a `.dat`) plays back through the live pipeline, so every window works on it as on the vehicle:

```bash
python -m wavi_py --replay D:\data\st_2026-11-02_1644_57.91_in_water_pilot2.jsonl --speed 2 --start 6:40
```

or pick **Replay** in the transport list, **Browse...** for the file and **Open**. Opening builds an index of the file (byte offsets, kinds, the fitted device clocks, the V0, the spikes, the events, the depth and the vehicle telemetry; ~3.5 s for a 13 min dive, with a progress bar) and caches it as `FILE.jsonl.idx.npz` next to the file, or under `%LOCALAPPDATA%\wavi_py` (`~/.cache/wavi_py`) if that folder is not writable; a changed file is re-indexed. The recording opens paused at `--start` (default 0); **Space** (or Pause / Play) plays, `--speed` / the speed box sets 0.25x .. 8x or max. 8x keeps up with every window open (measured with `tools/viz_bench.py --replay FILE --speed 8` on the cluster's software GL: the playhead at 8.00x, 2000 whisker and 800 IMU rows a second, the newest plotted sample < 0.8 s behind); max runs as fast as the file is read, for skipping ahead.

Times: every sample is placed on its device's clock (the ESP32's `tus`, the autopilot's RAW_IMU `time_usec`) fitted onto the Pi's receive clock when the index is built (`daq/clock.py`, as `whisker_link/convert.py`), so the whisker and IMU time axes are smooth and agree with each other; pacing follows the receive time. Live, the same mapping runs as a sliding-window fit. The V0 is the file's first 0.25 s of scans wherever playback starts, and the plots are zeroed with it as soon as the file opens, before anything is played.

**Despike** (panel checkbox, `daq/despike.py`). Replay shows the recording as it is by default; with Despike on, the scans are served with isolated spikes replaced. The test is a centred Hampel: a sample whose distance from the median of the 7 around it is more than 8 times the larger of the noise (median |first difference| / sqrt 2) and the residuals' spread (MAD of sample minus median of 7), both over ±25 samples (±100 ms), is replaced by that median. A run of up to 3 samples can be a spike; steps, ramps, fast deflections and the near-Nyquist zigzag the gauges carry under thrust are left alone, because they raise their own scale. The index finds the spikes over the whole file once (cached, sparse), the transport rewrites those scans as it serves them, and switching re-serves from the playhead. Live, the same test runs on the stream 28 samples late (112 ms at 250 Hz): the newest samples are shown raw and patched over the next ticks, and Rec writes each sample once final. Live it is on by default, off records and shows raw samples. The Dome view reads the bus, so it is not despiked live. On the pilot2 / vac_1102 recordings it replaces 34 samples in the 13 min dive, 19 in the 2 min dive and 3 in 18 min on the bench, nearly all 1 to 2 sample excursions at the onset of a hard contact. The old per-tick fill (`daq/outliers.py`, the MATLAB `filloutliers` port on each ~12-sample block) changed ~2 % of every recording's samples, almost all plain noise, and missed most of these, so the panel no longer uses it (only the reader's startup V0 does). The survey behind this (what the outliers are, how often, what each method does): `/scratch/bigeme/whisker_dev/replay_test/clean/index.html`.

**Whole recording in Line and IMU.** After the index, opening builds a store of the whole recording in the background (`replay/store.py`: every scan in mV and every RAW_IMU row with the attitude, on the fitted time axis, raw and despiked; ~3 s for the 13 min dive, ~3.5 s for the 18 min bench recording, then cached as `FILE.jsonl.store.npz` next to the index, which loads in ~0.05 s; 34 MB and 47 MB in memory). Until it is in, the windows draw the playback buffer as before. From then on the Line and IMU windows draw any span from the store, the whole recording included (zoom out with - or the wheel; R goes back to 30 s), min / max decimated per pixel column from a pyramid of block minima / maxima, so a full-range redraw costs about what 30 s does. Their values are exactly what the pipeline delivers (the tests compare them bit for bit), so Despike, Zero at... (any time of the recording now, not only the buffered 30 s) and the absolute-value labels (the 0.1 s before the playhead) work as before. A red **playhead** line runs through every plot. While following, the playhead is the right edge at the current span (near the start the window holds still and the line moves right across it; a span over the whole recording shows all of it); a pan or mouse zoom stops following, the playhead line keeps moving, and Live (L), Resume or a seek follows again at the shown span. With Link to Line off, the IMU window follows the playhead on its own, at 30 s or the span its own zoom sets.

The **timeline** (a dock at the bottom of the panel and of every view window, all on one model; the panel shows its own while a recording or live stream is open, the view windows' are hidden until their toolbar's **Timeline** toggle shows them) has the controls row (back / forward 5 s, play, speed, the position, the recording's wall clock and the depth at the playhead, and a **go to** box: seconds, `m:ss`, `40cm` for the next time the depth crosses 40 cm either way, `-40cm` for the previous one, `max` for the deepest point) over a strip with the depth (cm, from SCALED_PRESSURE2 against the surface pressure, the median over the disarmed start; fresh water, `WATER_DENSITY` in `replay/events.py` for sea water), the armed spans (green) and the events as ticks (hover for the text). Click the strip to go there, drag the red playhead to scrub, wheel / drag to zoom / pan time, double-click for all of it. The strip also shows the Line window's visible time span as a light red band with a thin red line at its right edge, on every timeline (panel and windows); it follows the Line window live and in replay (pan, zoom, following the playhead, scrubbing) and is gone while the Line window is closed (minimized it stays). It is display only: clicks, drags and the playhead go through it. It is told apart from the playhead by its line: 1 px, lighter red, drawn under the playhead (2 px, dark red, on top, grows on hover) and always the edge of a shaded band; while following, the two coincide and the playhead is what shows. The band is pinkish where it overlaps the green armed spans, so it does not read as selection 1's orange. **Scrubbing** moves the Line and IMU windows (and their playhead lines, and the playhead on every other timeline) with the mouse, at up to their 30 / 20 fps redraw cap, from the store, without waiting for the transport. The transport itself still gets a seek with 2 s preroll at most every 0.15 s during the drag and a full one (30 s preroll) on release, so during a drag the windows fed by the pipeline, Spectrum, FFT, Spec, Dome and ROV, jump in 0.15 s steps behind the mouse with what those short seeks served (FFT / Spectrum need their window of it, so they can show nothing between steps), and catch up fully on release. **Loop** repeats 5 s either side of the playhead (drag the blue range's edges). The event list and **event** buttons go to 2 s before an event. **ROV ▾** (or a right-click on the strip) adds the vehicle telemetry as lanes under the strip, picked by group from what the source has: pilot demand, thrusters, thrust per axis, current, climb, heading, vibration, and the flight mode / pilot gain band. There is one lane per unit (several variables share it, each in its own colour). The lanes share the strip's time axis and playhead: click to go there, double-click for all of it, hover for the values at the mouse. Each timeline has its own choice, and the last choice made is remembered (`timeline/rov_lanes` in the app settings), so new timelines start on it. A recording without the telemetry shows no lanes and keeps the choice. The Analysis window's timeline has the same variables in its Timeline column. Keys (panel): Space play / pause, Left / Right 5 s (Shift: 1 s), `,` / `.` previous / next event, `[` / `]` slower / faster.

Events: arm / disarm (HEARTBEAT from the autopilot, `[1,1]`, only), flight mode changes, every STATUSTEXT coloured by severity (the same text again within 10 s is one entry with a count), fault marks, whisker `seq` gaps, and ADC error counter increments from the server status (grouped per 10 s). A seek writes a line in the Fault log (it is not cleared). Live (Server transport), the timeline shows the same events and depth for the stream so far; a click there shows that time from the plot buffers (the last `t_buffer_s`; pause first to hold them).

Read-only: in replay the ESP32 commands, Scan mode, Reset ESP32 and Rec are disabled (the replay transport refuses commands with an error ack), Pause / Play drive playback, and **Reset** re-zeros at the newest samples. **Zero at...** (Line window, Q, then click a time) re-zeros the V0 and the Dome's tare from the 0.25 s round any buffered time, live, paused or in replay. **Export...** (timeline, replay only) saves the loop range (without Loop: the Line window's time span, which can now be the whole recording when zoomed out: the dialog's title shows the range) as a `.jsonl` clip or a `.dat` (`replay/export.py`). The clip is a byte copy of the range's lines after a copy of the hello and the newest info / status line, re-stamped to the range start (wall clocks kept); its hello carries the source's V0 and surface pressure, so the clip replays with the same zero and depth as the full recording, and `whisker_link.convert` reads it as any recording. The `.dat` is the recorder's format: mV as replay shows them (raw, or despiked with Despike on), each row's wall clock from the fitted scan time. The clip is always raw.

A `.dat` without its `.jsonl` (older recordings) opens too, whiskers only: it is converted once into a stream in the user cache (`replay/dat_source.py`, `%LOCALAPPDATA%\wavi_py\dat`), with no IMU, events, depth or status, and times that count samples as the recorder wrote them (its values were outlier-filled by the old per-tick fill when it was recorded; that can't be undone). Only the array's 32-gauge `.dat` is taken.

## Notes and recording cards

Every recording can carry notes in a sidecar next to it, `<stem>.notes.jsonl` (`replay/notes.py`), where the stem is the file name without its extensions (`replay/recname.py` reads both name formats: the laptop's `st_YYYY-MM-DD_HHMM_SS.ss_<tag>` and the Pi's `whisker_YYYYMMDD_HHMMSS[_<tag>]`; a laptop and a Pi name that start within 3 s are the same recording). The file is append-only JSON lines: a `note` (text, pinned to `t` seconds into the recording, or `null` for the whole recording), a `flag` (Mark bad, `keep: false`, with the reason as its text; Unmark bad is `keep: true`; the newest flag wins) or a `del` (removes a note; an edit is a del and a new note). Nothing is rewritten, so two copies (laptop and cluster) merge as the union of their lines by id (`notes.merge`). Each append is one locked write of one whole line, so two windows can note the same recording; a torn last line from a crash is skipped.

Which recording the notes go to: the open replay; while recording, the recording now; after it, the last one recorded (until a replay is opened). **Mark bad** works on all three (the vehicle's index too when the vehicle is live, see "Rec with the vehicle"), and its label and tooltip follow the notes' current flag. **Note...** (next to Mark bad, or **N** in the panel) asks for a text; it is pinned to the playhead in replay, or to now while recording, unless its box is cleared, which makes it a whole-recording note. While recording, "now" is the local copy's own time, the same session time its replay timeline shows (measured: within a few ms; the `.dat`-only serial transport uses the wall clock since Rec). The timeline shows the pinned notes as amber triangles with a dashed line (hover for the text, click to go there), tints its strip pink with a **BAD** label when the recording is marked bad, and has a **Notes (n)** button for the notes list: double-click a note to go to it, Add, Edit, Delete. A note added by another window shows up within 2 s.

Each recording also gets a card, `<stem>.card.json` (`replay/card.py`, ~12 kB): start, tag, duration, rate, channel, scan and IMU counts, spikes, ESP32 / ADC fault marks, depth range, armed time, a depth strip, and a preview: every gauge's RMS about its mean in 256 time bins, in dB re 1 mV, quantised between fixed limits of -40 and +15 dB (the ADC noise floor of a quiet gauge sits near -30 dB, touches reach +5 to +12 dB) so cards compare across recordings: touches show as bright streaks, dead gauges as black rows. Stop writes it in a low-priority child process (`tools/make_cards.py` on the closed `.jsonl`, or the `.dat`), so it never delays the next recording; on the 13 min dive that is ~6 s from the closed file (index 3.0 s, kept as usual; store 2.6 s, not kept; the card itself 0.12 s). For older recordings, or a folder on the cluster:

```bash
python -m wavi_py.tools.make_cards D:\data\rec [--force]
~/bin/onnode -- python -m wavi_py.tools.make_cards /shared/rc/whiskers/rov-recordings
```

It finds every recording under the folders (recursive), writes the missing and out-of-date cards (`--force`: all), and prints one line per recording.

Headless: `WaviClient(transport="replay", path="rec.jsonl", replay_speed=None)` plays a file as fast as it is read; `client.replay` is the transport (`seek`, `play`, `pause`, `speed`, `position`, `state`), `client.index` the index (events, `depth_at`, `depth_crossing`, `max_depth`).

## Selections and the Analysis window

**Selections.** A selection is a time window [t0, t1] on the recording's time axis, numbered and coloured. There is one set for the whole app, so every window shows the same ones. Turn on **Select** (Line and IMU toolbars, key **S**) and drag in a plot to make one; several are allowed. Each is a shaded region, labelled with its number at the bottom, in every Line plot (all three layouts), every IMU row, every timeline strip and every Analysis window's timeline. Drag an edge anywhere and it moves everywhere, and the Analysis windows redraw as you drag. Drag a region's body (anywhere between its edges) to move the whole selection, its length kept, in every plot and strip, with the Analysis windows following live; it stops at the source's extent (paused live: the extent of the copy). The cursor is an open hand over a body, a closed hand while dragging it, and the resize arrows over an edge. A drag that starts on a body therefore doesn't pan the plot; one that starts elsewhere still does. Where regions overlap, the newest is on top and takes the drag. With Select on, a drag on a body makes a new (overlapping) selection instead of moving it, and the body shows no hand. Right-click a region for **Compare**, **Spectrum**, **Spectrogram** (each shows that cell in the most recently focused Analysis window), **New analysis window** and **Delete**; **Del** deletes the one under the mouse. Replay: selections read the whole-recording store (raw or despiked, as Despike says), available once the store is in. Live: only while paused. Pause copies the buffers (the last `t_buffer_s`, ~3 MB for 90 s of 32 gauges, plus the depth so far), and the selections made during that pause read that copy, so they keep their data after Resume. An edge can't be dragged past what was copied. A new recording or stream clears the selections.

**Analysis windows** (the panel's **Analysis** button, in the Views row with Dome / ROV / Map: it raises the most recently focused one, or opens a new one if none is open; Go to → New analysis window; or a region's menu). A side panel has the **Selections** (an include box, the colour and number, t0 / t1 boxes that move the selection everywhere, ✕ to delete it) and the **Variables**. The whisker gauges are two small grids, **Plots** (what the 2x2 below shows) over **Timeline** (the timeline's own rows), independent of each other, laid out like the Dome view's plane map (`views/sensor_grid.py`: the dome map's sensor positions and names, port on the left and starboard on the right, each side as seen from inside facing it, its front column toward the centre gap; the sensors without a position on a row below). Each sensor is a box with its name over its A and B halves: a click on the name toggles both gauges (both on: both off, else both on), a click on a half toggles that gauge. A checked gauge is lit in its own colour (see Colour by), an unchecked one is grey, and a dead or not scanned one (the dome map's unused gauges; without a map the slots that are not wired) or one the stream does not have is hatched and dimmed; hover for the gauge's full name. The combo above the grids switches them to **by position (drag / lift)**: the same cells are then the dome's positions (LBU, LFM, ...), the left half its drag and the right half its lift, read through each recording's own dome map (`replay/dome_maps.dome_map_for`, stamped on a selection when it is made; live data: the active map) with polarity applied (a variable `pos:<position>:<axis>`, so one choice reads the same place on the dome in recordings wired differently; a half whose gauge is dead is dimmed). Gauge and position checks are kept separately, and both are drawn. **Plane map** (the box next to the combo, which turns on the position view) makes the Plots grid a small version of the Dome view's plane map without taking a cell of the 2x2. Each position's cell grows into a plot of its tip path over the included selections, in the selection's colour; with sub-ranges, each sub-range is its own path in that sub-range's line style. Events windows draw the highlighted events, else the picked one, in their group colour. The path is in degrees of bend through the position's sensor calibration (`deg_per_mv`, else the placeholder gain), with drag toward the side's front (right on the port side, left on starboard, marked by a tick on the front edge) and lift up. Every cell uses one scale, the largest bend drawn (the 99.5th percentile of each path, so a spike doesn't shrink the rest), shown as `±x°` above the grid. Arrows go from the root to the tip at each cursor (numbered; dragging a cursor moves them without re-reading the data), else at each path's peak bend. Without V0 a path starts from the median of its selection's first 0.25 s; with V0 (or an event's baseline) it starts from 0. The cells still pick variables: a click on the name or the plot toggles both axes, the **D** / **L** chips one each (`daq/plane_overlay.py`). Rows without a position stay compact. Below the grids, a tree with the same two columns has the rest: IMU accel x / y / z, gyro x / y / z, attitude roll / pitch / yaw, and depth, and the ROV group (see ROV variables), which also has the demand and the thrust per axis (how intended motion compares with achieved motion, next to accel and gyro). Timeline starts on Depth when the recording has depth, else on the first variable checked for Plots, and keeps that default until you edit the column. Each window has its own included selections, variables, cell sizes, cursors and options; several can be open. From a region's menu, Compare / Spectrum / Spectrogram go to the most recently focused Analysis window (a new one if none is open) and give that cell its space back if it was collapsed (Spectrogram also picks that selection), New analysis window opens another, and all of them pre-check that selection and the variables of the plot the menu opened in (that sensor's gauges in Line, that row's three series in IMU). A window from Go to includes every selection made so far; selections made later start unchecked. The Go to menu also lists the open Analysis windows. A hidden or closed window does no work (closing hides it, and the next new window reuses it).

**ROV variables.** A recording made through the server transport (and a live server stream) carries the vehicle's MAVLink, and the Variables then have an **ROV** group, so the whisker signals can be lined up with what the pilot asked for and what the vehicle did (only the autopilot's messages, `src [1,1]`; `replay/rov.py`). **Pilot** (RC_CHANNELS, ~19 Hz): forward (ch5), lateral (ch6), vertical (ch3, throttle), yaw (ch4), pitch (ch1) and roll (ch2), each (raw − 1500) / 400, so −1 .. +1 is full stick at 100 % gain (the pilot gain scales the stick: at 50 % they run ±0.5, as in the pilot2 dive). **Thrusters** (SERVO_OUTPUT_RAW servo1..8, ~19 Hz): the same scaling, labelled "thruster 1..8", with "(horiz)" / "(vert)" added when a PARAM_VALUE FRAME_CONFIG names a vectored frame (the pilot2 recordings have none, so they are numbered only); an output that reads 0 (unused) is left out. **Load / motion**: battery current (BATTERY_STATUS `current_battery`, MAVLink's cA, in A; SYS_STATUS's where there is none; 0.22 .. 56 A in the 13 min dive, a proxy of the thrusters' load), climb rate (VFR_HUD, m/s), heading (VFR_HUD, deg, **unwrapped**: a turn through north runs on past 360 or below 0, so the curve and its spectrum have no jumps) and vibration x / y / z (VIBRATION, m/s²). **Mode** is the flight mode, the armed state and the pilot gain (NAMED_VALUE_FLOAT PilotGain) as one band row on the timeline: a labelled band per mode span (MANUAL blue, ALT_HOLD yellow, ...; from the same HEARTBEAT parsing as the events), the armed spans as a green bar along its bottom and the gain as a step line on its 0 .. 1 axis. It is timeline-only (it has no Plots box). Each unit is its own row (pilot, thrust, A, m/s, hdg, m/s², below the IMU's and depth). The values are on the Pi's receive time, as the depth is, unevenly at about 19 Hz (3 Hz for current and vibration); the spectra take them as evenly spaced at their mean rate, as the IMU rows (so the pilot and thruster spectra reach 10 Hz). The index pass extracts them from the bytes of their lines (+0.6 s on the 13 min dive: 3.5 s instead of 2.9 s) and keeps them in its cache (`INDEX_VERSION` 3: an index cached before this is rebuilt once when the recording opens). Live, the stream's tracker collects them as the depth, and a paused copy keeps its own. A `.dat`-only recording, or one from the ESP32 / Sim transports, has none, and there is no ROV group.

**Layout.** Right of the panel: the **timeline** across the top, over a **2x2**. The left column holds the time axes: the **waveform** (top) and the **spectrogram** (bottom), which always show the same time span (zoom or pan one and the other follows). The right column holds the frequency axes: the **spectrum** of the windows (top) and the **spectrum at the cursors** (bottom). Drag the borders to resize. While all four cells are open, the left / right border is one line through both rows, so a time is at the same x in both left cells. Each cell collapses on its own with the **–** button at the right of its header. When a right cell collapses, its row's left cell takes the full width; the waveform and spectrogram then differ in width but still show the same time span. Collapsing both cells of a row gives the other row the whole height. Dragging a border to the edge collapses what it squashes (the shared border takes the whole right or left column). The collapsed cells are listed as buttons on a thin **Collapsed:** bar above the 2x2: click one to bring it back at the size it had. A collapsed cell is not drawn. The **□** button next to a cell's **–** expands it: it takes the whole 2x2 and the other three collapse; a second click on □, or any button on the Collapsed bar, puts back the layout from before the expand (sizes and the cells that were collapsed then). Double-click a border to share its space equally again. The timeline's lower border resizes it the same way. Toolbar: **Select** (S), **Clear sub-range** (Esc), **Zoom box** (Z), **Probe** (P), **Reset view** (R: the cell under the mouse; outside the cells, all of them), **Keys**, and **Colour by** selection | sensor.

**Colour by.** Each window has its own setting (the toolbar box; a new window starts on selection). **selection** (default): a trace takes its selection's colour and the variables in a row are told apart by its shade, as below. **sensor**: each gauge has one colour for the whole app, set by its index and not by what is shown, so it keeps its colour when other gauges are toggled: 16 hues, one per sensor, spread so that neighbouring slots differ, A darker and B lighter, at a moderate saturation so none reads as a cursor's saturated red, green, azure, magenta or black. The other variables of a row (IMU, depth, ROV) get a fixed dark colour by their place in the row. The selections are then told apart by line style, solid, dash, dot, dash-dot in their order (the top row's legend shows each selection's style in black), and their regions keep their selection colours. The grids, the grid legends and the timeline's gauge curves use the same gauge colours.

**Zoom box** (Z, as in the Line window): a drag in the waveform, the spectrum, the spectrogram or the cursor spectra zooms to the rectangle drawn (pyqtgraph pads it a little); off, a drag pans. The waveform and the spectrogram keep showing the same time span, and the zoom is kept until **R**. With Select on, a drag in the waveform still makes a sub-range.

**Timeline.** It shows the whole recording (live: the buffers so far) on absolute time, with one row per unit for the Timeline variables (depth goes down, as on the strip), min / max decimated to the plot's width over the visible span from the store's pyramid (`Dataset.overview`), so the 13 min dive draws as cheaply as a minute. With no Timeline variable a bare row remains, so the selections and playhead still show. Each row keeps at least 58 px, so its y labels don't overlap: the timeline starts 190 px tall (two rows) and grows with more rows, taking the room from the 2x2. The selections are the shared regions: drag an edge or the body, right-click for the menu, Del. The playhead is the red line. Mouse: a plain drag pans, the wheel zooms time, **Select** (S) + drag makes a new selection (included in this window), and a double-click seeks the replay there. A single click does nothing (no click-seek), so a near miss on a region doesn't move the playhead.

**Waveform** (top left) stacks one row per unit (mV, mg, mrad/s, deg, cm) on a linked X axis. X is the time from each selection's start, so the selections overlay at t = 0. A trace takes its selection's colour (the colour of its shaded region), and the variables in a row are told apart by the shade of that colour, dark to light in the order they are listed (or, with Colour by sensor, the gauge's own colour and the selection's line style). The gauges' row (mV) has the plane-map grid in miniature as its legend, the plotted gauges lit in their shade (grey) or, by sensor, in their colour, the others grey and the dead ones hatched (hover for the names). The other rows' legends list their variables in their shade (grey) or colour, and the top row's also shows the selections in their colour (by sensor: their line style). Gauges are drawn as the Line window draws them, (raw − V0) × scale, and the IMU in the IMU window's units: accel in mg, gyro in mrad/s, attitude in degrees. The curves are min / max decimated to the plot's width from the store's pyramid (`Series.envelope`; the two edge blocks are exact samples, so nothing from outside the selection shows), so a long selection redraws as cheaply as a short one. X follows the longest selection and Y fits the data until you zoom; **R** goes back to that. The cells read one `Dataset` (the included selections × the Plots variables, with the window's sub-range, `daq/analysis.py`): `traces(n)` for the waveform, `spectrum` and `spectrogram` for the spectra, which read every sample through `series().channels`. Depth is not in the series, so it comes from the source's depth (the timeline's). A click on a trace (within 5 px) shows that trace's (variable, selection) in the spectrogram, and the picked trace is drawn thick and on top. A click on the thick trace adds a cursor there (the header and tooltip say so). A click away from the traces does nothing.

**Sub-ranges.** With **Select** (S) on, each drag in the waveform makes another sub-range on the relative axis, numbered s1, s2, ...: a hatched band in every row (a different hatch each, labelled with its number; the selections are flat colours), whose edges and body drag (a body drag moves it, its length kept; with Select on, a drag that starts on a body makes a new one instead). Right-click a band, or **Del** with the mouse over it, to delete it. Each sub-range [a, b] stands for [t0 + a, t0 + b] of every included selection, clipped to its length; a selection shorter than a drops out of that one. With sub-ranges, the spectrum has one trace per (variable, selection, sub-range) and the spectrogram's picker has a third box for the sub-range; with none, the whole selections are used as before. Both cells say in their header which parts they use, and the spectrum's top legend names the sub-ranges with their range. **Clear sub-range** (Esc) clears them all and numbering starts at s1 again.

**Spectrum** (top right) shows the amplitude spectrum of every sample of each (variable, selection) in the whole selections, or of each (variable, selection, sub-range), on the waveform's rows, colours, shades and legends. The sub-ranges are told apart by line style (s1 solid, s2 dash, s3 dot, s4 dash-dot); with Colour by sensor, where the line style already marks the selection, each (selection, sub-range) pair has its own style in that order, listed in the top legend as "#1 · s2 ...". The amplitude convention is the Spectrum / FFT windows' (`daq/spectra.py`): a sine of amplitude a reads a, in the variable's unit, with whatever window (|rfft| × 2 / the window's sum, with the 0 Hz and Nyquist bins not doubled). Options on two lines: window **Hann** (default) or **Rectangular**, detrend **mean** (default), **linear** or **none** (the 0 Hz bin then shows the level); **log f**, **log amp** (on by default: the spectra span decades) and the frequency range. By default it runs from 0 to the highest Nyquist among the shown traces (the max box reads *Nyquist*: 125 Hz with gauges at 250 Hz, 50 Hz with only IMU rows) and follows it as variables change; a max you type stays until you set it back to its lowest. Each selection is taken at its own mean sample rate, so selections of different lengths each have their own frequency resolution (1 / length) and are not cropped to a common one. The IMU rows arrive a little unevenly and are treated as evenly spaced at that rate. A trace is recomputed only when its inputs change (the selection's span or its sub-range's, the options, Despike, that gauge's V0 / scale). Dragging an edge recomputes only that selection's traces, dragging a sub-range only that sub-range's, and a redraw with nothing changed does nothing.

**Spectrogram** (bottom left) shows one tile at a time at the full cell size: the (variable, selection) picked with the boxes at the left of its header, or by clicking a trace in the waveform (drawn thick there), and, while there are sub-ranges, which one (a third box: s1, s2, ...; the tile then covers that sub-range of the selection, still on the time from the selection's start). Time runs from the selection's start, on the waveform's axis (Hann, mean removed, as the Spec window). Options: **Seg** 0.25 / 0.5 / **1** / 2 / 5 s (frequency bins 1 / segment apart), **Ovl** 0 / 50 / **75** / 90 %, **dB**, and the colour range as in the Spec window, kept per unit group (mV, mg, ...). The controls show the picked variable's unit, so switching to accel and back keeps the gauges' range. **Auto** uses the 1st to 99.5th percentile of the tile; otherwise the min / max boxes apply, kept per unit and separately for linear and dB, and typing a value switches Auto off for that unit only. The colour bar runs across the top, so the plot stays as wide as the waveform's.

**Cursors.** A click in the spectrogram, or on the thick (picked) trace in the waveform, adds a vertical cursor at that relative time, drawn in both, labelled with its time from the selection's start (`t=12.34 s`; the label follows the cursor while it is dragged, in every row). Drag one to move it; right-click it, or **Del** with the mouse over it, to delete it (Del: a cursor first, then a sub-range, then a selection). The bottom right shows the picked tile's spectrogram column at each cursor (the segment whose centre is nearest), one curve per cursor in its colour, with the legend giving the cursor's time and the segment's centre (`t=12.34 s (segment at 12.25 s)`). It follows the spectrogram's dB box, and f runs from 0 to the tile's Nyquist. The cursor colours (red, green, azure, magenta, black) are saturated and solid, and none of them is a selection colour. In the spectrogram the lines have a white outline.

**Keys and Probe.** The Line window's keys act on the cell under the mouse (the one last under it, if the mouse is outside the window): **=** / **-** zoom X (keypad + / - too), **+** / **_** zoom Y of the row under the mouse, **.** / **,** zoom Y of all the cell's rows, the arrows move the data. In the waveform and spectrogram these move both (they are linked). A key zoom is kept until **R**. Keys typed into a box or a list are left to it. **Probe** (P) shows the values under the mouse in the status bar, with a vertical line: time and each curve of the row (waveform, timeline), frequency and each curve's amplitude (spectrum, cursor spectra; real f and amplitude with log axes), or t, f and the amplitude (spectrogram).

**Cost.** Only what changed is recomputed, nothing while hidden and nothing in a collapsed cell. An edge drag recomputes the dragged selection's spectra and, if it is the picked tile, the spectrogram; a cursor drag only takes columns out of the spectrogram already computed; the legends are re-labelled rather than rebuilt. Measured on the 13 min dive with 3 selections × 30 s × 4 gauges (12 traces) and 3 cursors, the whole window grabbed after each step (all four cells and the timeline painted): an edge drag 34 ms median, 46 ms max per update (about 10 ms without the paint), and a cursor drag 27 ms median, so both follow the mouse at the window's 20 fps cap. Re-measured with the grids, grid legends and sub-ranges (round 3), on one cluster node (skl-a-47, slower than the one above) against the code before them on the same node: no sub-range 62 ms median, 77 ms max edge drag (before: 59 / 62 ms) and a 27 ms cursor drag (before: 24 ms); with 2 sub-ranges (24 spectrum traces) 42 ms median, 49 ms max (45 / 46 ms by sensor), and a 26 ms cursor drag: shorter spans to transform, so cheaper than the whole 30 s.

## Events: comparing manoeuvres across recordings

**What an event is.** Each recording gets a manoeuvres sidecar, `<stem>.manoeuvres.json` (`replay/manoeuvres.py`): the pilot's stick (the RC demand per axis, surge / sway / heave / yaw, rest within ±0.02) cut into holds and the transitions between them (onset, release, step, reversal), each with its class (`single:surge+`, `combo`, ...), level, mode, depth, the projected thrust (the stick and the thrusters as the ROV variables read them: `replay/rov.py`, from the index), the motion response, and per dome position the drag / lift baseline, peak, steady value, time constant and band RMS against a clean, reference-drift-corrected baseline. An event is one transition or hold, with a window of 2 s before to 5 s after its time. The dome map per recording (`replay/dome_maps.py`: the map history, or the map line a new recording carries after its hello) says which gauge is which position and which whisker set was on, so recordings with different maps compare by position.

**Sidecars.** Stop writes the sidecar next to the recording in a second low-priority child, after the card (it uploads with the recording, like the card and the notes; the index and store caches don't). Opening a recording in the replay reads it, or builds it in the background when it's missing or older than the recording (next to the recording, or in the user cache when that folder isn't writable); the timeline's lane shows once it's there. For older recordings, or a folder on the cluster (shared lab data: write the sidecars elsewhere with `--out`):

```
python -m wavi_py.tools.make_manoeuvres D:\data\rec [--force] [--jobs 4]
~/bin/onnode -- python -m wavi_py.tools.make_manoeuvres /shared/rc/whiskers/rov-recordings/2026-11-05 --out /scratch/$USER/manoeuvres --jobs 6
```

Each output folder also gets `events.csv` (one row per event and position) unless `--no-csv`.

**Entry points.** An Events window is the Analysis window in its Events mode; it opens from: the control panel's **Events** button or Go to → Events... (the open recording, else the last scope); the Recordings browser's **Events...** (the selected rows, or a date / tag with everything under it; Ctrl / Shift for several; cluster-only ones are downloaded first through the verified download, or skipped with a note in the panel); and the Analysis timeline's **stick lane** (Selections mode, when the recording has its sidecar): bars per segment, coloured by axis and sign (minus darker), stronger with the level, rest empty, the coast after a release hatched, combos grey; hover for class, level and duration; a click makes a Selection of that event's window; right-click → **Compare similar...** opens an Events window on the same type and class, level ±0.1 and mode over the recording's folder, with that event pinned.

**Filters and grouping.** The panel holds the scope (the recordings and folders, with a count; **Add recordings...**, **Add folder...**, **Remove**) and the filter: type, axis and sign, the |u| range, mode, minimum hold, clean baseline, steady, minor inputs (any / none / at most a level), the depth range, alive (any; no position lost; every position known alive), the whisker set; and **Group by** (run, day, whisker set, mode, level with its bin edges, none). A change re-runs the query after a short pause; it reads only the sidecars (~0.25 s), the recordings' stores stay in a shared cache, so only a new recording costs a store build (~2.5 s per 5 min, in the background with a progress line; the window keeps responding and draws what it has).

**Browsing.** The top cell has the events table (group swatch, recording, t, type, class, level, mode, depth, flags: clean, steady, minor, no reference, lost positions; and a feature column chosen above it: steady / peak / band RMS / tau / rise of a position's drag or lift, or a motion feature) and a scatter (x the level or a feature, y the feature, colour the group). They share one selection: a click or Ctrl / Shift click in either, a lasso (**Lasso**, then draw) in the scatter. Hover or select draws the event thick in the waveform. A double-click (or **Open in the replay**) opens the recording in the replay 2 s before the event. The waveform shows the time from each event's onset (a dashed t = 0 line), thin lines per event in its group's colour (fainter the more there are), and per group a darker, white-outlined median with its 25–75 % band; at most 200 traces are drawn (pinned first, then spread over the set), with "drawn N of M" in its header. **Dome grid** lays the Positions out as the variable grids do, on the Dome view's plane map (port left, starboard right, each side seen from inside, front columns toward the centre: LB LF | RF RB; rows U, M, L), drag solid, lift dashed, one y range per row, other variables in a row above; off, the panels fill a grid in the checked order. The spectrum and spectrogram show the picked event (the first selected, else the first drawn); there is no group median spectrum. Probe reads the thick events and the medians; Zoom box, the cells' expand button and the cursors work as in Selections mode. **Variables** in an Events window: the grid starts in its by-position view with every position's drag and lift checked (the gauge view is there too, but a gauge is a different place on the dome in recordings wired differently); the tree has the IMU and the ROV's per-axis demand and thrust (`rov:fwd` ..., `rov:th_surge` ...: the same in every recording with a vehicle; the rest of the ROV group is per recording, so it is listed in Selections mode only). There is no Timeline column (no timeline). Colour is always the group (**Colour by** is off), and **Select** / sub-ranges are off: the event waveform's time is the onset's, and the spectra read the picked event whole.

**Curation and saved comparisons.** The table's checkbox, or the context menu (**Exclude / Include / Pin / Unpin / Show only these / Include all**) of the selected events in either half, edits the query's curation: excluded events stay listed (greyed, an x in the scatter), pinned ones are always drawn. **Save as...** stores the whole query (scope, filter, grouping, curation) as a named comparison (a JSON file in the settings folder, `WAVI_COMPARISONS_DIR` to override); the combo loads one, **Revert** reloads it, **Delete** removes it.

## Cluster sync

Recording is always local first; with **auto-upload** on, each recording goes to the lab's cluster folder after Stop (the laptop's own copies: the `.dat`, the `.jsonl`, the `.faults.txt`, and the `.notes.jsonl` / `.card.json` when there are any). Layout: `/shared/rc/whiskers/rov-recordings/YYYY-MM-DD/<stem>.*`, the date being the recording's start. The rebuildable caches (`.idx.npz`, `.store.npz`) stay local.

The app uses your own OpenSSH: `ssh -o BatchMode=yes <host>`, with your key and `~/.ssh/config`. It never asks for or stores a password, and it never answers a host-key question (BatchMode fails instead). Each file is piped through ssh into `<name>.part` on the cluster; the same remote command checks its size and sha256 against the local file and only then renames it into place, group-writable (`umask 002`, `chmod g+rw`). A file the cluster already has with the same size and hash is skipped. No scp: piping avoids its drive-letter (`C:\...` reads as host `C`) and remote-quoting pitfalls, so there is one code path on every OS.

**Notes** (`.notes.jsonl`, append-only, `replay/notes.py`) are merged, never overwritten, in one ssh call: the local copy goes up, and on the cluster, under `flock` on the date folder, the remote copy gains the lines whose id it lacks and is printed back; the laptop then appends the lines it lacks, under the same lock the GUI's own note appends take, so a note added while a sync runs is never lost. Two laptops syncing the same recording's notes at once are serialized by the remote lock, so neither loses the other's. Copies hold the same notes in a different line order, so notes are compared by their ids, not by hash. A note added on another machine comes down with the next push of that recording.

**The card** (`.card.json`) is written by a child process a few seconds after Stop. The recording's files go up at once without it; the card's arrival queues the recording again, and that push sends only the card.

**Record row.** The status line reads *off*, *ok*, *uploading 3/20 st_..._tag.jsonl 45%* (the recording's place in this push, the file, its bytes; also *hashing* and *verifying*), *queued (n, offline)*, *paused (n queued)* or *error: reason*; it is elided in the middle to fit, the tooltip has the full text, the bytes of the file and of the push, the rate and the ETA, and a click opens the Uploads window. **Cluster...** sets the host (an `~/.ssh/config` alias, e.g. `sporcsubmit.rc.rit.edu`), the folder, auto-upload, pruning and keep-N, **Upload existing...** counts the recordings in the output folder not yet on the cluster (auto-upload only sends new ones), lists them and, if you agree, queues them; they go when you press OK. **Test** runs `mkdir -p <folder> && test -w <folder>` and says why it failed: no ssh on PATH, host key unknown, auth refused, timeout, not writable. The settings live in QSettings (the registry on Windows, a plist on macOS, `~/.config/wavi_py/wavi_py.conf` on Linux).

**Uploads window** (click the status line, **Uploads...** in Cluster..., or Go to → Uploads... in any view window; one window, raised if open). A list of every recording in the upload queue and of those finished in this session, each expandable to its files: the queue first (in upload order), then the finished ones, newest first. Columns: the recording (date, time, tag) or file; the status (queued, waiting: in use by recording or replay, checking the cluster, hashing, uploading, verifying: the cluster checks the size and sha256, done, skipped: already on the cluster, failed with the reason, offline, removed); a bar while it is being worked on; the size; and when it finished, or why it failed. The header shows the push: recording k of n, MB done of the MB total (skipped files count as done), the rate over the last 10 s and an ETA, then the connection (ok, offline or error with the reason and the time of the next retry, paused). **Retry now** tests and pushes at once instead of at the next 5-min retry. **Pause** stops after the file being sent (it completes and stays recorded) and starts no push until **Resume**; it is not kept across restarts. **Remove from queue** (also in the right-click menu) only dequeues, never deletes a file; Upload existing... queues it again. **Clear finished** empties the finished rows (the newest 200 are kept anyway). A done row's right-click menu copies its cluster path. The queue is read from `sync_state.json` on a thread, so after a restart or offline the window shows what is waiting with its last error.

**Progress, how.** An upload feeds the file into ssh's stdin through a pipe in 1 MB pieces from a thread and counts the bytes (at most 4 updates a second); the count runs ahead of the wire by ssh's buffers (a few MB), which is why a file shows *verifying* after its last byte while the cluster checks it. The timeout, cancel (closing the app kills the call), the no-console-window flag on Windows and the verification (`.part`, size, sha256, rename) are unchanged. Hashing a large file locally reports its progress too. The worker thread reports a structured event per step (`SyncEvent` in `remote/sync.py`) through a Qt signal; the status line and the window both draw from it (`remote/progress.py`, `remote/uploads.py`), never polling the worker. A real push from a compute node to sporcsubmit (a 300 MB and a 40 MB synthetic file, the 2-min pilot, a small recording with three files already there) sent 399 MB in 17 s, about 24 MB/s.

**Queue.** Recordings waiting to upload are kept in `sync_state.json` in the user data dir (`%LOCALAPPDATA%\wavi_py`, `~/Library/Application Support/wavi_py`, `~/.local/share/wavi_py`), with the size, mtime and sha256 of every file verified on the cluster. The queue survives restarts; a push that fails (offline, link dropped) leaves the recording queued, a dropped transfer leaves only a `.part` that the next try overwrites, and the GUI retries every 5 min. A recording uploaded before whose files changed since (a note added, a card written later) is queued again by that retry. A push first runs the connection test unless the last one passed, so offline it only queues.

**Pruning** (off by default) keeps the newest N recordings in the output folder (default 10) and deletes older local copies only when every file is verified on the cluster: the recorded upload matches the local file and a fresh remote listing confirms the size and sha256. The recording being written and the one open in replay are never touched. The first time, the GUI lists what would go and asks; saying no turns pruning off.

**Command line** (same settings, queue and code; for when the GUI isn't running):

```bash
python -m wavi_py.tools.wavi_sync test
python -m wavi_py.tools.wavi_sync push [PATH ...] [--verify]   # default: the queue + the output dir
python -m wavi_py.tools.wavi_sync status
python -m wavi_py.tools.wavi_sync prune [--yes]                 # lists only, unless --yes
```

`--host`, `--root`, `--dir`, `--keep` override the settings for one run (`--save` stores them). `push` leaves recordings modified in the last 20 s alone (the GUI may be writing one); it prints a line per file (hashing a large one, uploading, done, already on the cluster, failed with the reason) and a percentage line at most every 3 s. Exit code 2 means offline.

**One-time setup** (every OS): an ssh key that logs in without a password (with a key, RIT RC asks for no Duo), and a host entry. Then check it in a terminal: `ssh -o BatchMode=yes sporcsubmit.rc.rit.edu true` must return without a prompt (the first plain `ssh sporcsubmit.rc.rit.edu` accepts the host key).

```
# ~/.ssh/config (Windows: C:\Users\<you>\.ssh\config)
Host sporcsubmit.rc.rit.edu
    User <your RIT username>
    IdentityFile ~/.ssh/id_ed25519
```

- **Linux / macOS:** `ssh-keygen -t ed25519`, then `ssh-copy-id sporcsubmit.rc.rit.edu`. A key with a passphrase needs an agent: macOS add `UseKeychain yes` and `AddKeysToAgent yes` to the host entry and run `ssh-add --apple-use-keychain ~/.ssh/id_ed25519` once; Linux desktops usually run an agent already (`ssh-add -l`).
- **Windows 10/11:** Settings → System → Optional features → **OpenSSH Client** (usually installed; `ssh -V` in PowerShell shows it). For a key with a passphrase, start the agent once in an admin PowerShell: `Get-Service ssh-agent | Set-Service -StartupType Automatic; Start-Service ssh-agent`, then `ssh-add $env:USERPROFILE\.ssh\id_ed25519` as yourself. Create the key with `ssh-keygen -t ed25519`; Windows has no `ssh-copy-id`, so append it on the cluster: `type $env:USERPROFILE\.ssh\id_ed25519.pub | ssh sporcsubmit.rc.rit.edu "cat >> ~/.ssh/authorized_keys"`. The app finds `ssh.exe` on PATH or in `C:\Windows\System32\OpenSSH`, and runs it without a console window.

## Recordings browser

**Recordings...** (next to Browse... in the File row, and in every view window's Go to menu) opens a window with two tabs: **Local** (the output folder and the download cache) and **Cluster** (the cluster folder of Cluster sync). Both show a tree, date → tag → recordings, newest first. A row has the recording's number in its date and tag group (#1..n by start time, counted at display time over every known recording, so it is the same in both tabs and under a filter), the start time, the duration, the card's preview strip (one pixel row per gauge, time left to right, the inferno map of the cards: dead gauges are dark lines, touches bright spans), a **BAD** badge (the reason in its tooltip), the comment count and where it lives (local, cluster, both, queued for upload). A laptop recording and the Pi's file of the same run (starts within 3 s) are one row. The Browse... dialog is unchanged.

**Events...** opens an Events window on the selected rows (a date or tag: everything under it; Ctrl / Shift for several); see Events above. Selecting a row shows the card's numbers and the notes. A recording with a local copy takes a note here (**Add note...**); a cluster-only one's notes are read-only until it is opened. **Make card** builds a missing card of a local recording in the background; a cluster-only recording without one says in its tooltip how to make it there (`~/bin/onnode -- python -m wavi_py.tools.make_cards <folder>` from a wavi_py checkout). The filter box matches tag, file name and note text; **Hide bad** hides the flagged ones.

**Open** (or a double-click) replays a local copy at once. A cluster-only recording is first downloaded into the cache in two ssh calls (the cluster's sha256 of every file, then one `cat` of them all, split by size, each file checked and only then renamed; progress and Cancel), then replayed. The 2-min pilot dive (40 MB) from sporcsubmit took 3.5 s, and 4.1 s from Open to replay. The cache is `cluster_cache` in the user data dir, capped at 20 GB: the least recently opened recordings go first, never the open one, never one with notes not yet synced. A downloaded recording is recorded as already uploaded, so sync never sends it back, and the cache is a folder sync watches: a note added to it in replay goes up with the normal sync.

**Refresh** lists the cluster in one ssh call: per date folder its mtime, every file's size and mtime, and the content of every card and notes file. The catalogue is cached locally (`catalog.json` in the user data dir) and a refresh walks only the date folders whose mtime changed (every upload and notes merge ends in a rename in the folder, which changes it); the label shows its age. The same call deletes leftover `.wavi_notes.*` temporaries older than a day. Offline or not set up, the Cluster tab says why and the Local tab keeps working. A note appended on the cluster by hand (not through the sync) doesn't change the folder's mtime, so the catalogue misses it until something else there changes.

## Run (library / headless)

```python
from wavi_py import WaviClient

client = WaviClient(transport="tcp", host="192.168.2.3", port=5555,
                    nsensor=9, fs=80)
client.start()
client.wait_ready(timeout=10)

last_seq = 0
while running:
    samples, last_seq = client.bus.read_since(last_seq, block=True, timeout=0.1)
    if samples is None:
        continue
    # samples: np.ndarray, shape (N_new, nch), dtype float32, raw post-parse
    action = my_agent.act(samples[-1])
    motor.send(action)

client.stop()
```

Or run the included example:

```bash
python wavi_py/examples/headless_control_loop.py --host 192.168.2.3
```

The GUI and a headless control loop can run **simultaneously** in separate processes — each is just another subscriber on the bus inside its own `WaviClient`.

## Architecture (one diagram)

```
[Transport]  ──bytes──►  [DAQ thread]  ──samples──►  [SampleBus]  ──┬──►  [Qt UI subscriber]   plot + record
   TCP/serial                parse                    ring buffer    │       (this process)
                             align V0                 cond var       │
                                                                     ├──►  [agent control loop]
                                                                     │       (this process,
                                                                     │        own thread)
                                                                     │
                                                                     └──►  [recorder, ...]
                                                                            (anywhere)
```

Each subscriber tracks its own `last_seq`; slow ones can't backpressure the producer (the bus is bounded, oldest data dropped if a reader falls behind by more than `t_buffer × Fs` samples — detect via `new_seq - last_seq > len(samples)`).

## Verification checklist

1. **GUI vs MATLAB parity**: open the same recording (`.dat`) in both MATLAB ([data_processing/plot_sensor_signal.m](../data_processing/plot_sensor_signal.m)) and Python — outputs should match byte-for-byte.
2. **Decoupling**: run `wavi_py/examples/headless_control_loop.py` and `python -m wavi_py` simultaneously against the same Pi. Neither should affect the other; latencies from `bus.publish` to control-loop's `read_since` return should stay under a few ms even when the GUI is being dragged around.
3. **Disconnect/reconnect**: in the GUI, click Disconnect mid-stream then Connect — clean resume. Headless: `client.stop()` then `client.start()` does the same.
